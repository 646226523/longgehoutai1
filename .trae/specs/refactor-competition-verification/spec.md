# 赛事核验功能重构 Spec

## Overview
- **Summary**: 重构现有的“赛事核验”功能，将其从“单点下拉选择”模式升级为“列表展示+批量处理+设备联动”的高效操作模式。新功能包括赛事核验看板、进度可视化、批量核验操作、核验详情页以及扫码设备联动模拟。
- **Purpose**: 提升赛事核验的批量处理效率，让管理员能一眼掌握所有赛事的核验状态，并支持扫码设备联动实现高效核验。
- **Target Users**: 公棚/鸽会的赛事管理员、核验员。

## Goals
- [Primary goal 1] 将核验入口从“下拉选择”重构为“列表展示”，实现所有赛事核验进度的全局可视化。
- [Primary goal 2] 实现核验进度条和状态标签，直观展示每场赛事的核验完成率。
- [Primary goal 3] 支持跨赛事的批量核验和导出操作。
- [Primary goal 4] 提供扫码核验和手动核验两种方式，并模拟扫码设备联动。
- [Primary goal 5] 新增核验统计看板，展示总参赛羽数、已核验、待核验、异常等核心指标。

## Non-Goals (Out of Scope)
- **真实硬件集成**: 本次迭代不包含与真实 RFID 扫码枪等物理硬件的驱动程序对接，仅实现 UI 层面的联动模拟和 Web API 对接预留。
- **复杂的权限分级**: 权限控制沿用现有 `competition:verify` 权限，不实现“核验员”等细分角色的复杂权限隔离。
- **DNA 比对算法**: 核验逻辑（基因匹配）沿用现有实现，不改动算法本身。

## Background & Context
- **Current State**: 当前 `admin-web/src/pages/competition/Verify.tsx` 实现为一个下拉选择器，用户必须先选择一场赛事，然后在一个扁平的表格中逐羽核验。这种模式效率低下，无法总览全局，也不支持跨赛事批量操作。
- **Technical Context**:
    - 前端使用 React + Ant Design + ProTable。
    - 后端使用 Express + SQLite。
    - 已有 `competition_participants` 表和核验相关的 API（`/api/competition/:id/participants/verify`）。

## Functional Requirements

### 1. 核验列表页 (VerifyList)
- **FR-1.1**: 页面顶部展示赛事筛选器，支持按赛事名称、公棚（主办方）、日期、状态进行筛选。
- **FR-1.2**: 以表格形式展示所有赛事，列包含：赛事名称、主办方、参赛羽数、已核验数、核验率（进度条）、状态标签（待核验/核验中/已核验/异常）。
- **FR-1.3**: 每行提供操作按钮：`开始核验`（跳转详情页）、`查看详情`。
- **FR-1.4**: 支持行选择功能，可多选后进行“批量核验”或“批量导出”操作。
- **FR-1.5**: 页面底部/顶部提供“核验统计”看板，展示全局汇总数据。

### 2. 核验详情页 (VerifyDetail)
- **FR-2.1**: 点击“开始核验”后进入该页，展示单场赛事的详细信息和参赛鸽列表。
- **FR-2.2**: 参赛鸽列表支持搜索足环号、按核验状态筛选（全部/待核验/已核验/异常）。
- **FR-2.3**: 每行展示足环号、鸽主、核验状态、操作（核验/复核/查看详情）。
- **FR-2.4**: 提供核验操作：点击“核验”按钮，自动匹配基因档案，更新状态。
- **FR-2.5**: 页面集成“扫码设备联动”区域，显示设备状态（模拟）和最新扫描记录。

### 3. 批量核验逻辑
- **FR-3.1**: 列表页支持勾选多场赛事，点击“批量核验”按钮，对选中赛事执行批量核验。
- **FR-3.2**: 批量核验操作需调用后端批量接口，并实时反馈结果（成功/失败数量）。

### 4. 扫码设备联动 (模拟)
- **FR-4.1**: 核验详情页提供设备状态指示器（🟢已连接 / 🔴已断开）。
- **FR-4.2**: 提供模拟扫码输入框，输入足环号后自动触发核验流程。
- **FR-4.3**: 扫描结果实时反馈，包括核验通过、不通过、重复扫描等状态。

## Non-Functional Requirements
- **NFR-1**: 列表页加载时间 < 1s，核验操作响应时间 < 300ms。
- **NFR-2**: 进度条和状态标签必须清晰、直观，色彩符合常规认知（绿=完成，红=异常，黄=进行中）。
- **NFR-3**: 代码结构清晰，组件化拆分，便于后续扩展（如接入真实硬件）。

## Constraints
- **Technical**: 
    - 前端框架：React, Ant Design v5, ProComponents.
    - 后端框架：Node.js, Express, SQLite.
    - 必须兼容现有数据库结构。
- **Business**: 
    - 需兼容现有 `competition:verify` 权限体系。

## Assumptions
- 假设当前公棚/鸽会管理员有权查看所有赛事。
- 假设扫码设备联动初期仅需前端模拟，后端预留接口即可。
- 进度条所需统计数据（总羽数、已核验数）可通过现有 SQL `COUNT` 聚合查询获得。

## Acceptance Criteria

### AC-1: 列表页展示所有赛事核验状态
- **Given**: 系统中存在多场不同核验状态的赛事
- **When**: 管理员进入“赛事核验”页面
- **Then**: 看到所有赛事的列表，每行显示进度条和状态标签
- **Verification**: `programmatic`

### AC-2: 批量核验功能可用
- **Given**: 列表页有多场待核验的赛事
- **When**: 管理员勾选多个赛事并点击“批量核验”
- **Then**: 系统批量执行核验，并弹出结果反馈
- **Verification**: `programmatic`

### AC-3: 核验详情页逐羽操作
- **Given**: 管理员进入某场赛事的核验详情页
- **When**: 对单羽参赛鸽点击“核验”按钮
- **Then**: 系统更新该鸽的核验状态，并在列表中实时反映
- **Verification**: `programmatic`

### AC-4: 扫码设备联动模拟
- **Given**: 管理员在核验详情页
- **When**: 在模拟扫码框输入一个合法的足环号
- **Then**: 系统模拟扫码成功，自动核验该参赛鸽，并显示在扫描记录中
- **Verification**: `human-judgment` (交互体验)

### AC-5: 进度与状态可视化
- **Given**: 任何赛事
- **When**: 查看其在列表中的状态
- **Then**: 进度条百分比与核验状态标签颜色、文案准确对应
- **Verification**: `human-judgment` (UI/UX审查)
